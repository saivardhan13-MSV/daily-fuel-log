# Daily Fuel Log: Python API

FastAPI backend for the tracker. The Next.js app keeps the UI and the Supabase
login; this service owns the data logic. Requests carry the user's Supabase
access token, and every query runs **as that user**, so Postgres Row Level
Security stays the final isolation layer (the anon key is used, never the
service-role key).

```
Next.js UI --(Bearer token)--> FastAPI --(user's JWT)--> Supabase Postgres (RLS)
```

## Run

```bash
cd backend
python -m venv .venv
.venv/Scripts/activate            # macOS/Linux: source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env              # or leave empty: falls back to ../.env.local
uvicorn app.main:app --reload --port 8010
```

Interactive docs at `http://localhost:8010/docs`.

## Test

```bash
pytest
```

The suite has no network dependency. Routers depend on a `Repository`
protocol, so the API tests run against an in-memory fake; the Supabase
implementation is exercised separately against a real project.

## Layout

| Path | Responsibility |
| --- | --- |
| `app/domain/` | Pure logic with no I/O: date validation and range bounds, macro totals, Mifflin-St Jeor targets, streaks, trend totals, quick-add ranking |
| `app/repo.py` | `Repository` protocol and the Supabase implementation (user-scoped queries) |
| `app/auth.py` | Verifies the Bearer token with Supabase Auth; `user_id` only ever comes from it |
| `app/routers/` | HTTP endpoints and request validation |
| `app/food_search.py` | USDA FoodData Central lookup (fails soft) |
| `tests/` | Domain, API and auth tests, plus a golden parity file |

## Design notes

- **No client-supplied `user_id`**, on any route. A test asserts it.
- **Dates are calendar strings.** `2026-02-30` and `2026-13-40` are rejected
  (a regex alone would accept them). No UTC conversion anywhere, so a date
  cannot shift around midnight or DST.
- **"Not logged" is not "zero".** Daily totals are zero-filled for a stable
  chart axis, but each day carries `logged`, so averages and target-hit counts
  only ever use days the user actually logged.
- **Port parity is tested, not assumed.** `tests/fixtures/ts_target_parity.json`
  holds 810 outputs generated by running the original TypeScript
  `calculateTargets`; the Python port must match all of them. (Python's
  `round()` is banker's rounding, JS `Math.round` is half-up, so a naive port
  would drift by 1 on ties.)
- **Bounded queries.** Range endpoints cap at 90 days; the streak and
  quick-add reads have fixed row limits. Nothing downloads full history.

## Status

Phases 1-3 are done: read endpoints, write endpoints, and the Next.js app can
route all of its data and writes through this API. The old direct-to-Supabase
code is still in place as the default; removing it (and choosing where to host
this API) is Phase 4.

## Using it from the Next.js app

Opt-in via one server-only env var in the repo's `.env.local`:

```
API_URL=http://localhost:8010
```

- **Unset (default):** the app queries Supabase itself, exactly as before.
- **Set:** pages read through `src/lib/data.ts` and Server Actions call this
  API through `src/lib/api.ts`, forwarding the user's Supabase access token.
  Action signatures, validation messages and `revalidatePath` calls are
  unchanged, so no component changed.

Both modes render identical pages for the same account (compared page by page),
and every write action was exercised through the UI in API mode.

`/api/streak`, `/api/trends` and `/api/weight-logs` accept an optional
`today=YYYY-MM-DD` so the two services slice the same window even when they
run in different timezones. It is trusted only within +/-1 day of this
server's date, like the future-date check on writes.

If the API is down, pages show the app's existing "Something went wrong / Try
again" screen and the cause (e.g. `ECONNREFUSED`) is logged by the Next.js
server; actions return a short "Couldn't reach the server" message.

## Write endpoints

| Endpoint | Replaces |
| --- | --- |
| `POST /api/entries`, `DELETE /api/entries/{id}`, `DELETE /api/day?date=` | `addEntry`, `removeEntry`, `clearDay` |
| `POST /api/copy` (`section: null` = whole day) | `copyEntries` |
| `PUT /api/custom-foods` | `upsertCustomFood` |
| `POST /api/water/add`, `POST /api/water/reset` | `addWater`, `resetWater` |
| `PUT /api/body-targets` | `saveBodyTargets` (targets are computed server-side) |
| `PUT /api/weight-logs`, `PATCH`/`DELETE /api/weight-logs/{id}` | `logWeight`, `updateWeightLog`, `deleteWeightLog` |

- Bodies use `extra="forbid"`, so a `user_id` (or client-computed macros) is a
  422, not silently ignored. The repository stamps `user_id` from the token.
- Errors are `{"detail": "<one readable string>"}`. Database failures are
  logged server-side and surface only as a generic message ("Failed to add
  item"), never Postgres text.
- Stricter than the TypeScript where that relied on the database: food names
  and quantities, UUID ids, target ranges, and NaN/Infinity (Python's JSON
  parser accepts them) are all rejected up front.
- Copy re-reads the source rows on the server and inserts them in one batch;
  it rejects a source date on or after the destination.
- Water add is a read-modify-write like the original (PostgREST has no atomic
  increment), so two simultaneous taps can lose one. Fine for a one-person tap
  counter; an RPC would fix it if it ever mattered.
