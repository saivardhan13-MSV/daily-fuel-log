# Daily Fuel Log: Python API

FastAPI backend for the tracker. The Next.js app keeps the UI and the Supabase
login; this service owns the data logic. Requests carry the user's Supabase
access token, and every query runs **as that user**, so Postgres Row Level
Security stays the final isolation layer (the anon key is used, never the
service-role key).

```
Next.js UI --(Bearer token)--> FastAPI --(user's JWT)--> Supabase Postgres (RLS)
```

## Run

```bash
cd backend
python -m venv .venv
.venv/Scripts/activate            # macOS/Linux: source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env              # or leave empty: falls back to ../.env.local
uvicorn app.main:app --reload --port 8010
```

Interactive docs at `http://localhost:8010/docs`.

## Test

```bash
pytest
```

The suite has no network dependency. Routers depend on a `Repository`
protocol, so the API tests run against an in-memory fake; the Supabase
implementation is exercised separately against a real project.

## Layout

| Path | Responsibility |
| --- | --- |
| `app/domain/` | Pure logic with no I/O: date validation and range bounds, macro totals, Mifflin-St Jeor targets, streaks, trend totals, quick-add ranking |
| `app/repo.py` | `Repository` protocol and the Supabase implementation (user-scoped queries) |
| `app/auth.py`, `app/jwt_verify.py` | Verifies the Bearer token (signature checked locally against Supabase's public JWKS); `user_id` only ever comes from it |
| `app/routers/` | HTTP endpoints and request validation |
| `app/food_search.py` | USDA FoodData Central lookup (fails soft) |
| `tests/` | Domain, API and auth tests, plus a golden parity file |

## Design notes

- **No client-supplied `user_id`**, on any route. A test asserts it.
- **Dates are calendar strings.** `2026-02-30` and `2026-13-40` are rejected
  (a regex alone would accept them). No UTC conversion anywhere, so a date
  cannot shift around midnight or DST.
- **"Not logged" is not "zero".** Daily totals are zero-filled for a stable
  chart axis, but each day carries `logged`, so averages and target-hit counts
  only ever use days the user actually logged.
- **Port parity is tested, not assumed.** `tests/fixtures/ts_target_parity.json`
  holds 810 outputs generated by running the original TypeScript
  `calculateTargets`; the Python port must match all of them. (Python's
  `round()` is banker's rounding, JS `Math.round` is half-up, so a naive port
  would drift by 1 on ties.)
- **Bounded queries.** Range endpoints cap at 90 days; the streak and
  quick-add reads have fixed row limits. Nothing downloads full history.

## Status

The Python API is the app's only data layer: the Next.js app has no direct
database queries left. Phases 1-4 are done (read endpoints, write endpoints,
cutover of the Next.js app, deployment on Vercel), and production runs through
it. The original TypeScript query code was removed once the deployed API was
verified; it is in git history if you ever need to compare behaviour.

## Using it from the Next.js app

One required server-only env var in the repo's `.env.local` (and in the
Next.js Vercel project, for every environment you deploy):

```
API_URL=http://localhost:8010      # or the deployed API's URL
```

Pages read through `src/lib/data.ts` and Server Actions call the API through
`src/lib/api.ts`, forwarding the user's Supabase access token. Login and the
session cookie stay in Next.js; the API verifies the token and runs every query
as that user. Without `API_URL` the app shows its error screen and logs
"API_URL is not set".

`/api/streak`, `/api/trends` and `/api/weight-logs` accept an optional
`today=YYYY-MM-DD` so the two services slice the same window even when they
run in different timezones. It is trusted only within +/-1 day of this
server's date, like the future-date check on writes.

If the API is down, pages show the app's "Something went wrong / Try again"
screen and the cause (e.g. `ECONNREFUSED`) is logged by the Next.js server;
actions return a short "Couldn't reach the server" message.

## Write endpoints

| Endpoint | Replaces |
| --- | --- |
| `POST /api/entries`, `DELETE /api/entries/{id}`, `DELETE /api/day?date=` | `addEntry`, `removeEntry`, `clearDay` |
| `POST /api/copy` (`section: null` = whole day) | `copyEntries` |
| `PUT /api/custom-foods` | `upsertCustomFood` |
| `POST /api/water/add`, `POST /api/water/reset` | `addWater`, `resetWater` |
| `PUT /api/body-targets` | `saveBodyTargets` (targets are computed server-side) |
| `PUT /api/weight-logs`, `PATCH`/`DELETE /api/weight-logs/{id}` | `logWeight`, `updateWeightLog`, `deleteWeightLog` |

- Bodies use `extra="forbid"`, so a `user_id` (or client-computed macros) is a
  422, not silently ignored. The repository stamps `user_id` from the token.
- Errors are `{"detail": "<one readable string>"}`. Database failures are
  logged server-side and surface only as a generic message ("Failed to add
  item"), never Postgres text.
- Stricter than the TypeScript where that relied on the database: food names
  and quantities, UUID ids, target ranges, and NaN/Infinity (Python's JSON
  parser accepts them) are all rejected up front.
- Copy re-reads the source rows on the server and inserts them in one batch;
  it rejects a source date on or after the destination.
- Water add is a read-modify-write like the original (PostgREST has no atomic
  increment), so two simultaneous taps can lose one. Fine for a one-person tap
  counter; an RPC would fix it if it ever mattered.

## Auth modes

`AUTH_MODE=jwks` (default) checks the token's signature locally against the
public keys Supabase publishes at `/auth/v1/.well-known/jwks.json`. Only
`ES256`/`RS256` are accepted (never `HS256` or `none`), and audience, issuer,
expiry and subject are all required. There is no secret to store and no
Supabase round trip per request, which is what makes it suitable for
serverless.

The trade-off: a token stays valid until it expires (an hour by default) even
if the user signs out elsewhere, because nothing asks Supabase. PostgREST
behaves the same way (signature and expiry only), so Row Level Security
accepts exactly the tokens this API accepts. `AUTH_MODE=remote` asks Supabase
Auth on every request instead, at the cost of one extra network call.

## Deploy on Vercel

The API is its own Vercel project, separate from the Next.js app, so the live
site is untouched until you opt in with `API_URL`. Config lives in this folder:
`pyproject.toml` (dependencies and `entrypoint = "app.main:app"`),
`requirements.txt`, `.python-version`, `vercel.json` and `.vercelignore`.

1. Vercel dashboard -> **Add New -> Project** -> import this same GitHub repo.
2. Set **Root Directory** to `backend`. The framework preset should detect
   FastAPI.
3. Add environment variables (all environments):

   | Name | Value |
   | --- | --- |
   | `SUPABASE_URL` | same as the app's `NEXT_PUBLIC_SUPABASE_URL` |
   | `SUPABASE_ANON_KEY` | same as the app's `NEXT_PUBLIC_SUPABASE_ANON_KEY` |
   | `USDA_FDC_API_KEY` | same as the app's (optional; food search is empty without it) |

   Do **not** add the service-role key: this API never uses it.
4. Deploy, then check `https://<your-api>.vercel.app/api/health` returns
   `{"status":"ok"}` (and `/docs` for the interactive API docs).
5. In the **Next.js** Vercel project -> Settings -> Environment Variables, add
   `API_URL` = the API's URL (no trailing slash) for Production, then redeploy.
6. Put both projects in the same Vercel **region** as your Supabase project
   (Settings -> Functions) to keep the hops short.

Deploying from the CLI instead (what was used for the first deploy):

- Create/link the project from `backend/` with `vercel link --yes --project
  <name> --scope <team>`, then set the project's **Root Directory** to
  `backend` (dashboard, or `vercel api /v9/projects/<id> -X PATCH -f
  rootDirectory=backend`; in Git Bash prefix with `MSYS_NO_PATHCONV=1`).
- Deploy from the **repo root** with `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID`
  set (see `backend/.vercel/project.json`). Do not run `vercel link` at the
  repo root: it writes a `.env.local` there and would overwrite the Next.js
  app's real one.
- Once Root Directory is `backend`, pushes to `main` redeploy the API through
  the connected GitHub repo.

To roll back a bad API release, redeploy the previous deployment of the API
project from the Vercel dashboard (Deployments -> ... -> Promote to
Production). The Next.js app only needs `API_URL` to keep pointing at the same
URL.

The API is publicly reachable but every route except `/api/health` needs a
valid Supabase access token, and every query then runs as that user under Row
Level Security.
